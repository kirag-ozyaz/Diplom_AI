# Инструкция к пункту 2. Исправить проверку поиска

Это инструкция по доработке кода, не готовый исправленный оценщик. Файлы проекта проверены на версии 16295a8acc347d9e891186d4a8657d55ff0807b8. Изменения и прогоны мной не выполнялись.

## 1. Подготовить отдельные входные и выходные файлы

1. Распаковать ранее выданный PUE_268_gold_v3.zip.
2. Положить eval_questions_gold_268.json в корень своей рабочей копии проекта. Эталоны не помещать в data/raw, data/extracted или data/chunked: они не должны попасть в поисковую базу.
3. Сохранить старые результаты отдельно. Новые результаты записывать под новыми именами, не подменять ими предыдущие без пояснения смены методики.
4. На время исправления не менять модель, параметры поиска и переранжирования: сначала исправить измерение. Если меняется нарезка, отметить это как отдельное изменение эксперимента.

## 2. Исправить чтение набора вопросов

Файл: scripts/stage4_eval/lib/eval_questions_io.py.
Функция: _normalize_row.

Сейчас она создаёт новый словарь только с id, registry_id, query, expected_clause и section. Остальные поля нового набора теряются при загрузке.

Изменить функцию: сначала копировать исходную запись целиком, затем нормализовать перечисленные старые поля. Сохранить массивы required_clauses и required_tables, эталоны mandatory_answer_facts, source_paths, split, split_group и ограничения источников. Не преобразовывать массив пунктов в строку.

Проверка: после вызова load_eval_questions у всех 268 записей доступны новые поля; для составного вопроса required_clauses содержит все его обязательные пункты. Идентификаторы вопросов не перенумерованы.

## 3. Закрепить принадлежность фрагментов

Файл: src/preprocessing/Create_chunkeds/md_to_chunked_2.py.
Функции: chunk_document и create_chunk_obj.

Поле metadata.Clause уже существует — использовать его как исходную принадлежность, но проверить правильность присвоения на границах пунктов. Не извлекать принадлежность поиском всех похожих номеров в content.

Дополнить записи следующими сведениями (это предлагаемые новые поля):
- document_id — идентификатор документа;
- corpus_version — версия снимка исходников;
- clause_id — собственный пункт, из проверенного metadata.Clause;
- parent_clause_id и part_index — связь частей одного пункта;
- table_ids — идентификаторы действительно содержащихся таблиц;
- chunk_id — воспроизводимый идентификатор фрагмента.

Не использовать случайный UUID или встроенный Python hash как основу воспроизводимости. Идентификатор можно строить из версии документа, пункта, номера части и SHA-256 содержимого. Повторная обработка тех же данных должна давать те же идентификаторы.

Перекрёстные ссылки, если нужны, хранить отдельно: они не входят в clause_id или table_ids. Упоминание «см. таблицу …» не означает, что таблица содержится во фрагменте.

Проверка: у каждого оцениваемого фрагмента определены источник и принадлежность. Записи без принадлежности явно помечены и не засчитываются по догадке. Табличные заголовки, единицы, строки и существенные примечания сохраняются вместе либо связаны явными идентификаторами.

## 4. Передать эти сведения через Milvus до оценщика

Файл: src/preprocessing/Create_embeddings/multimodal_rag.py.

Исправить последовательно:
1. Схему коллекции: добавить необходимые поля происхождения.
2. load_from_jsonl_folder и load_from_jsonl_folder_async: заполнять их из записей JSONL. При списочной вставке порядок значений обязан соответствовать схеме.
3. search_text: включить поля в output_fields и в возвращаемые словари результатов.
4. Проверить, что вариант с переранжированием сохраняет эти поля после перестановки результатов.

Сейчас базовая схема сохраняет chunk_id, source_file и chapter, но собственного Clause в ней нет; search_text его не возвращает. Поэтому изменения только оценщика недостаточно.

Создать отдельные проверочные коллекции с новой схемой и загрузить туда исправленные данные штатными загрузчиками проекта. Старые коллекции пока не удалять. Для base, e5 и rerank сохранить соответствующие настройки моделей и префиксов. Затем направить проверочные конфигурации на новые коллекции.

Проверка: взять реальный результат search_text и сопоставить его chunk_id, clause_id и текст с исходной записью JSONL. Проверить это во всех трёх режимах. При отсутствии метаданных оценщик должен выдавать ошибку валидации, а не возвращаться к поиску номера в тексте.

## 5. Разметить релевантность содержимого

Создать отдельный файл разметки релевантности — далее называем его retrieval_qrels.json. Это НОВЫЙ файл, в проекте его наличие не предполагается.

Для каждого вопроса указать:
- обязательные пункты и таблицы из нового набора;
- идентификаторы фактов из mandatory_answer_facts (назначить устойчивые идентификаторы);
- какие chunk_id действительно подтверждают какие факты;
- какие связанные части нужны для таблицы, условия или исключения.

Сопоставлять по исходному содержанию, а не по тому, что нашёл текущий поисковик. Возможен полуавтоматический подбор кандидатов по clause_id, но итоговое соответствие нужно проверить. Полный список релевантных фрагментов формируется из корпуса, а не только из успешной выдачи.

Отдельно отметить ограничения вопросов №36 и №252: не заставлять оценщик угадывать отсутствующую или неоднозначную норму. Наличие номера пункта не снимает ограничения источника.

Проверка: правильный пункт без нужного факта может получить попадание по пункту, но не попадание по содержанию. Общие формулировки и упоминание числа без его условий не подтверждают факт целиком.

## 6. Заменить правило попадания во всех оценщиках

Файлы:
- scripts/stage4_eval/retrieval/eval_retrieval_hitk.py;
- scripts/stage4_eval/retrieval/eval_retrieval_hitk_e5.py;
- scripts/stage4_eval/retrieval/eval_retrieval_hitk_rerank.py;
- scripts/stage4_eval/retrieval/mrr_ndcg/eval_retrieval_rank.py.

Сейчас clause_in_text ищет номер в тексте. В ранговом оценщике rank_info использует такое же правило. Убрать этот механизм из принятия решения о релевантности. Общее правило вынести в одну общую функцию, чтобы четыре скрипта не разошлись.

Для каждого k считать отдельно:
1. Hit по пункту: найден хотя бы один собственный clause_id из required_clauses в нужном документе/версии.
2. Покрытие пунктов: сколько РАЗЛИЧНЫХ обязательных пунктов найдено из общего числа обязательных.
3. Hit по содержанию: найден хотя бы один фрагмент, подтверждающий обязательный факт по проверенной разметке.
4. Покрытие фактов и полное покрытие: собраны ли все обязательные применимые факты и необходимые таблицы/условия.

Повторная ссылка на пункт не считается его нахождением. Несколько частей одного пункта не увеличивают число найденных пунктов, но могут дополнять покрытие фактов. Не удалять такие части из фактической выдачи: иначе изменится смысл k. Повторы одного и того же chunk_id не должны приносить дополнительную пользу.

## 7. Исправить ранговые метрики и сводки

Файл: scripts/stage4_eval/retrieval/mrr_ndcg/rank_metrics.py.

Вести отдельные результаты для принадлежности пункту и полезного содержания. MRR считать по первой релевантной позиции соответствующего вида; при глубине 10 явно указывать ограничение MRR@10.

Для nDCG сначала зафиксировать единицу релевантности:
- если это пункты, повторные части уже найденного пункта не дают новый выигрыш, а идеальный список строится по обязательным пунктам;
- если это фрагменты с содержанием, релевантность задаётся проверенным retrieval_qrels.json, а идеальный список строится по всем размеченным релевантным фрагментам.

Не смешивать число пунктов в знаменателе с количеством полезных фрагментов в числителе. Для начала достаточно бинарной релевантности; градуированную шкалу вводить только вместе с явными критериями и соответствующим расчётом идеального порядка.

Проверить функции сравнения и построения сводок: сейчас часть из них пересчитывает показатели только по позиции первого попадания. Такой пересчёт потеряет сведения о нескольких релевантных фрагментах. Сводки должны использовать новые полноценные результаты, а не восстанавливать nDCG из одного rank.

В деталях сохранять полученные chunk_id, собственные пункты, подтверждённые факты, позиции, оценки поиска и недостающие обязательные элементы. Общие метрики дополнительно разделять по development и reserved_evaluation. Зарезервированную часть не использовать для настройки.

## 8. Проверить ловушки до полного прогона

Добавить тесты рядом с scripts/stage4_eval/retrieval/mrr_ndcg/test_rank_metrics.py:

1. Чужой пункт содержит ссылку на нужный: попадания нет.
2. Нужный пункт найден, нужного факта в его части нет: попадание по пункту есть, по содержанию нет.
3. Другая часть того же пункта содержит факт: содержательное попадание есть.
4. Из двух обязательных пунктов найден один: полное покрытие не засчитано.
5. Есть только ссылка на таблицу: сама таблица не найдена.
6. Несколько повторов одного фрагмента: покрытие не увеличивается.
7. Нужный номер из другого документа/версии: попадания нет.
8. Нет метаданных: явная ошибка, не запасной поиск номера в тексте.
9. Проверить заранее рассчитанные небольшие примеры MRR и nDCG; nDCG не выходит за диапазон 0–1.

Сначала все тесты должны пройти. Потом выполнить небольшой проверочный прогон и вручную сверить сохранённую выдачу со своими отметками.

## Когда пункт 2 считать выполненным

- Метаданные проверены и доходят до оценщика без потерь.
- Новый набор читается с обязательными пунктами, фактами и разделением.
- Содержательная релевантность размечена независимо от удачной выдачи.
- Все проверки ловушек пройдены.
- Для трёх режимов получены новые результаты по одинаковым правилам и данным.
- Для каждого спорного попадания можно показать конкретный источник и подтверждённый факт.

Рост метрик не является условием успеха: после устранения ложных попаданий они могут снизиться. Успех — корректное измерение, а не красивые проценты.
