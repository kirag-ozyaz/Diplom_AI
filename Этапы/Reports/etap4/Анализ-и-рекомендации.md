### 2. Быстрые улучшения retrieval (код + переиндексация)

**E5-префиксы**  
У вас `intfloat/multilingual-e5-base`, а в `multimodal_rag.py` при индексации и в `search_text` вызывается `encode(query)` **без** `query:` / `passage:` (в комментариях это уже описано, в коде — нет). Для E5 это типичная причина слабого retrieval.

- При индексации: `passage: {текст чанка}`
- При поиске: `query: {вопрос}`
- После правки — **заново** `load_data.py` (новые векторы).

**Фильтр по разделу**  
В вопросах есть `section`; в Milvus есть поля вроде `chapter`. Если сузить поиск по разделу (или по главе из `expected_clause`), Hit@k на ПУЭ часто растёт. Сейчас `search_text` вызывается без фильтра (`eval_retrieval_hitk.py`, цикл по `questions`).

**Параметры Milvus**  
В `search_text` стоит `ef: 64` — для большой коллекции можно поднять `ef` / проверить индекс (HNSW). Эффект меньше, чем у префиксов, но бесплатно попробовать.

### 3. Данные и чанки

- **Один пункт — один чанк** (у вас по сути так: `Clause` в metadata, текст с «Пункт 1.1.1») — хорошо; не раздувать чанки на несколько пунктов.
- В **текст для эмбеддинга** явно дублировать: `Пункт {Clause}. {content}` — усиливает связь «вопрос → номер пункта».
- **Покрытие индекса**: все ли разделы ПУЭ из 300 вопросов реально в `load_data`? Если вопрос на пункт, которого нет в коллекции, Hit@k не вырастет.

---

### 4. Модель эмбеддингов

| Вариант | Заметки |
|---------|---------|
| Оставить **multilingual-e5-base** + префиксы | Минимальная смена стека |
| **BAAI/bge-m3** | Сильный мультиязычный retrieval; свои правила инструкций; снова полный `load_data` |
| **intfloat/multilingual-e5-large** | Тяжелее, но лучше качество; нужна VRAM |

Менять модель имеет смысл **после** префиксов и проверки разметки — иначе непонятно, что дало прирост.

---

### 5. Двухступенчатый поиск (сильно, но больше работы)

1. Dense top‑20 из Milvus  
2. **Reranker** (cross-encoder, например `cross-encoder/ms-marco-MiniLM` или мультиязычный) по паре (вопрос, текст чанка)  
3. Hit@k считать уже по rerank top‑5  

Для диплома это хороший «этап улучшения» в отчёте.

---

### 6. Реестр вопросов (часто даёт «ложное» падение с 68% до 12%)

- **300 вопросов** — не все с ручной проверкой `expected_clause`; tests24 + правила в `CLAUSE_RULES` могут ставить **не тот пункт**.
- Для сдачи можно честно держать два набора: **база 38/74** (ручная разметка) и **расширенный 300** (жёстче, ниже метрика) — в Word так и писать.
- Улучшение: выборочно пройти промахи, поправить `expected_clause` или удалить «не-ПУЭ» вопросы.

---

### 7. Что *не* поднимет Hit@k (но нужно для этапа 4)

- Смена **Ollama 14B** — влияет на generation/judge, **не** на Hit@k (там LLM не используется).
- Только **увеличение k** в отчёте без смены поиска — метрика @5 уже 28%; нужен лучший ранжир, а не k=10 в проде.
