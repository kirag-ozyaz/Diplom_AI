### 2. Быстрые улучшения retrieval (код + переиндексация)

**E5-префиксы**  
У вас `intfloat/multilingual-e5-base`, а в `multimodal_rag.py` при индексации и в `search_text` вызывается `encode(query)` **без** `query:` / `passage:` (в комментариях это уже описано, в коде — нет). Для E5 это типичная причина слабого retrieval.

- При индексации: `passage: {текст чанка}`
- При поиске: `query: {вопрос}`
- После правки — **заново** `load_data.py` (новые векторы).

**Фильтр по разделу**  
В вопросах есть `section`; в Milvus есть поля вроде `chapter`. Если сузить поиск по разделу (или по главе из `expected_clause`), Hit@k на ПУЭ часто растёт. Сейчас `search_text` вызывается без фильтра (`eval_retrieval_hitk.py`, цикл по `questions`).

**Параметры Milvus**  
В `search_text` стоит `ef: 64` — для большой коллекции можно поднять `ef` / проверить индекс (HNSW). Эффект меньше, чем у префиксов, но бесплатно попробовать.

### 3. Данные и чанки

- **Один пункт — один чанк** (у вас по сути так: `Clause` в metadata, текст с «Пункт 1.1.1») — хорошо; не раздувать чанки на несколько пунктов.
- В **текст для эмбеддинга** явно дублировать: `Пункт {Clause}. {content}` — усиливает связь «вопрос → номер пункта».
- **Покрытие индекса**: все ли разделы ПУЭ из 300 вопросов реально в `load_data`? Если вопрос на пункт, которого нет в коллекции, Hit@k не вырастет.

### 4. Модель эмбеддингов

| Вариант | Заметки |
|---------|---------|
| Оставить **multilingual-e5-base** + префиксы | Минимальная смена стека |
| **BAAI/bge-m3** | Сильный мультиязычный retrieval; свои правила инструкций; снова полный `load_data` |
| **intfloat/multilingual-e5-large** | Тяжелее, но лучше качество; нужна VRAM |

Менять модель имеет смысл **после** префиксов и проверки разметки — иначе непонятно, что дало прирост.

3. Hit@k считать уже по rerank top‑5  

Для диплома это хороший «этап улучшения» в отчёте.

### Изменение префиксов для улучшения качества

**E5-префиксы (`query:` / `passage:`)** — **да, имеет смысл**, но только **парой**: и при индексации чанков, и при поиске. Сейчас у вас и запрос, и пассажи идут **без** префиксов; добавить только к запросу — **нельзя**. После правки нужен **пересчёт эмбеддингов и перезаливка Milvus**, затем новый Hit@k. Ожидание: **небольшой**, но реальный прирост Hit@k (порядка нескольких процентов), не «удвоение».

**Фильтр по главе/разделу** — **для вашей оценки на 268 вопросах — нет** (эталон известен, раздел из вопроса автоматически не извлекается; ошибочный фильтр отрежет правильный пункт). Имеет смысл **позже в боте**, если появится надёжное определение раздела ПУЭ — и лучше как **сужение/буст**, а не жёсткий `chapter == …` на всём пайплайне.

**Rerank** — **да, если цель — качество ответа и citation**, а не только Hit@k. При Hit@5 ≈ **81%** часть промахов — «пункт есть, но не в top-5»; реранкер по top-20 часто **поднимает** нужный чанк. Цена: **задержка и VRAM/CPU**; для этапа 4 уже не обязательно, для **этапа 5 / защиты** — один из самых практичных шагов **после** (или вместе с) корректных E5-префиксов.

**Порядок по отдаче:** сначала **согласованные E5-префиксы + переиндексация**, потом **rerank на top-k**; **фильтр** — только под сценарий с явной метаданной, не для текущего eval. Generation и judge сильнее выиграют от **rerank + retrieval**, чем от смены только промпта LLM.

## Практический порядок внедрения

1. **E5 `query:` / `passage:`** + перезаливка Milvus → `run_hitk.ps1` → сравнить с таблицей выше.  
2. **Rerank** (top-20 → 5) → перепрогон **generation live** на том же *N*.  
3. **Фильтр по разделу** — только для бота/eval с явным `section`, не в общем Hit@k.

Итого: **сейчас** — один проход dense search, E5 без инструкций, k=5, без rerank и без фильтра в eval. **Предлагается** — сначала **исправить E5 + переиндекс**, затем **rerank** для ответов; **фильтр** — точечно, не как замена первым двум шагам.
---

**Префиксы** здесь — это короткие **служебные подписи в начале строки** перед тем, как текст отдаётся в модель эмбеддингов. Модели семейства **E5** (у вас `intfloat/multilingual-e5-base`) при обучении видели разные «роли» текста, и авторы рекомендуют явно помечать их.

## Для E5 обычно так

| Роль | Префикс | Пример |
|------|---------|--------|
| **Запрос пользователя** (поиск) | `query: ` | `query: Какой цвет у нулевого рабочего проводника N?` |
| **Документ / чанк в индексе** (пассаж) | `passage: ` | `passage: Пункт 1.1.29. Цвета изоляции...` |

Вектор считается **не от чистого вопроса**, а от строки **с префиксом**. Запрос и чанки кодируются **по разным правилам**, но **согласованно**: в индексе везде `passage:`, при поиске — `query:`.

## Зачем

Одна и та же модель училась различать «ищем» и «храним в базе». Без префиксов E5 часто работает **хуже**, чем задумано для retrieval (хотя у вас уже ~81% Hit@5 и без них — префиксы могут **поднять** метрику, а не «включить» поиск).

## Что у вас сейчас

В коде префиксы **описаны в комментариях**, но **не добавляются**: и чанки при заливке в Milvus, и вопрос при `search_text` идут **как обычный текст**.

## Важно

- Нельзя повесить только `query:` на поиск, а в базе оставить старые векторы без `passage:` — пространство эмбеддингов «разъедется».
- Нужна **пара**: `passage:` при индексации + `query:` при поиске → потом **перезаливка Milvus** и новый Hit@k.

Это **не** промпт для Ollama и **не** префикс в чанке ПУЭ («Пункт 1.3.8…») — только **техническая метка для SentenceTransformer/E5** перед encode.
