# Конвертация старых чанков и отдельное объединение с V2

Это дополнение к уже установленной поставке V2 с подготовкой чанков 1_5. Архив содержит только новые скрипты, инструкцию и результаты проверок. Он НЕ содержит готовую замену корпуса и не изменяет основной пайплайн. Разархивировать в корень проекта, где рядом находятся `data`, `scripts` и `V2`. Имена файлов внутри архива обычные, номер поставки находится только в имени ZIP.

Нужен Python 3.9 или новее. Зависимости, Docker, модели, Milvus и доступ к сети не требуются. Скрипты нужно запускать из корня проекта. По умолчанию корень определяется по расположению папки скриптов, а не по текущей папке PowerShell. Можно явно передать `--project-root`.

## Папки

- `data/chunked` — исходные старые JSONL и подпапки `image_*`; только чтение.
- `data/chunked_V0` — преобразованная старая версия со скопированными ресурсами и архивом происхождения.
- `V2/data/chunked` — текущая автоматическая нарезка V2; только чтение.
- `V2/results/convert_chunked_V0_to_V2/plan` — план сопоставления без активного объединённого корпуса.
- `V2/data/chunked_merged` — отдельно создаваемый кандидат объединённого корпуса.

Исходные `data/raw`, `data/chunked` и `V2/data/chunked` не меняются. В базу ничего не загружается. Ни один скрипт не переключает конфигурацию V2 на новый корпус. Выходная папка должна отсутствовать; существующая, даже пустая, не перезаписывается. Для повторного запуска задайте новую папку через `--output`; удалять или заменять старые результаты автоматически скрипт не будет.

## 1. Преобразовать старый корпус

```powershell
python scripts/convert_chunked_V0_to_V2/convert.py
```

Будут обработаны все JSONL непосредственно в `data/chunked`. Результат записывается в `data/chunked_V0`. Подпапки с изображениями не рассматриваются как дополнительные корпуса. Документ сопоставляется с V2 только при единственном совпадении имени исходника. Неизвестное или неоднозначное имя вызывает ошибку, а не пропуск документа.

Если нужны только девять первых глав, вместо предыдущей команды:

```powershell
python scripts/convert_chunked_V0_to_V2/convert.py --chapters 1.1 1.2 1.3 1.4 1.5 1.6 1.7 1.8 1.9
```

При другом расположении старого набора укажите `--input относительная/папка`. Все переданные папки должны находиться внутри проекта. При неоднозначном имени можно указать `--document-map путь/карта.json`. Это JSON-объект, где ключ — старое `metadata.source_file` или имя JSONL, значение — точное `source_file` документа из V2. Для разных документов с одним и тем же старым именем сначала явно разделите/уточните источники, не подбирайте соответствие по номеру пункта.

Проверить результат:

```powershell
python scripts/convert_chunked_V0_to_V2/check.py
```

Ожидаемый технический статус — `technical_preservation_passed`. Он означает сохранность текста/ресурсов и учёт строк, НЕ правильность формул и НЕ разрешение финального скоринга.

## 2. Сначала получить план объединения

```powershell
python scripts/convert_chunked_V0_to_V2/merge.py
```

Эта команда сохраняет план и снимки обоих входов, но не создаёт активные объединённые JSONL. Список различающихся пар находится в:

`V2/results/convert_chunked_V0_to_V2/plan/_audit/conflicts.json`

Общий отчёт:

`V2/results/convert_chunked_V0_to_V2/plan/_audit/report.json`

Сопоставляются документ, область нумерации `Scope` и собственный `Clause`, а не встретившиеся в тексте перекрёстные ссылки. Все части большого пункта выбираются вместе. Различие текста может быть лишь отличием контекстного заголовка или изображения от LaTeX; число конфликтов не является числом нормативных ошибок.

## 3. Явно собрать отдельный кандидат

Пример политики для сохранения ручных глав 1.1–1.9: при совпавшем собственном пункте этих глав брать целиком ручной вариант; для остальных совпавших пунктов оставлять V2. Это выбор кандидата, а не подтверждение, что выбранный текст лучше или нормативно верен.

```powershell
python scripts/convert_chunked_V0_to_V2/merge.py --apply --prefer-v0-chapters 1.1 1.2 1.3 1.4 1.5 1.6 1.7 1.8 1.9
```

Для иной политики измените список глав. Альтернативный явный вариант `--apply --prefer-v2` оставляет V2 при всех совпадениях. Без явной политики `--apply` запрещён. Пункты, найденные только в V0, добавляются как требующие проверки. Ручные блоки без однозначного собственного пункта, включая приложения, сохраняются в архиве для отдельного разбора, а не дублируются рядом с автоматическими. Их статус в отчёте — `archived_unassigned_requires_review`; игнорировать их при окончательной приёмке нельзя.

Все невыбранные варианты, исходные JSONL и используемые ресурсы сохраняются в `_audit/inputs/v0` и `_audit/inputs/v2` внутри результата. Для каждой входной строки отчёт указывает выходные ID либо причину сохранения только в архиве. Вложенный аудит конвертации V0 также сохраняется. Это не посимвольное слияние двух редакций одного пункта: таблицы и формулы двух вариантов автоматически не смешиваются.

Если V2 изменился после конвертации V0, объединение блокируется. Нужно заново преобразовать V0 в новую выходную папку относительно нового V2 и передать эту папку в `merge.py --v0 ...`. Старые результаты при этом не перезаписываются.

Проверить полученный кандидат:

```powershell
python scripts/convert_chunked_V0_to_V2/check.py --output V2/data/chunked_merged
```

После этого нужно разобрать различия и принадлежность таблиц, проверить формулы/числа по источнику и отдельно согласовать использование нового корпуса. Старые qrels нельзя автоматически считать действующими: ID и корпус изменились, их привязку нужно пересобрать/перепринять. Здесь нет команды загрузки в Milvus или финального скоринга.

## Что именно сохраняется и проверяется

- Текст, формулы и таблицы переносятся без содержательной очистки и без исправления математической разметки. В частности, очистка служебных маркеров из автоматической подготовки 1_5 не применяется автоматически к ручному тексту.
- Меняются только локальные назначения ссылок на ресурсы. Каждая замена имеет точные позиции, исходную строку, новую строку и SHA-256 ресурса. Оригинальные байты файлов сохраняются. Внешние ссылки не скачиваются и учитываются в отчёте.
- Слишком длинный текст делится на части не более 60 000 байт UTF-8. Склейка частей точно восстанавливает исходный текст после замен ссылок. Разбиение внутри длинной таблицы или формулы всё равно требует смысловой проверки.
- У ручного импорта нет выдуманных DOCX-offsets и SHA-256 исходного DOCX. `source_file` обозначает логически сопоставленный документ, но реальное происхождение текста — архивный JSONL, его строка, ID и хеши. Совпадение имени исходника не доказывает совпадения редакций нормативного документа.
- Старые метаданные сохраняются в `legacy_metadata`. Пустой `Chapter` заполняется только из иерархического собственного номера. Неоднозначные короткие номера и области нумерации не угадываются.
- Проверка воспроизводит замену ссылок по исходным архивным строкам, сравнивает склеенный текст и все хеши файлов, проверяет учёт всех входных строк, уникальность ID, части и связанные ID. Статусы `reviewed`, `ready_for_final_scoring=true` не выставляются.
- Не найденный локальный ресурс, выход за пределы папки, абсолютный файловый путь, неоднозначный документ, повтор ID, повреждённый JSON и неполные части приводят к ошибке без публикации частичного результата.

Отчёт и архив `_audit` являются обязательной частью результата. Их нельзя удалять перед объединением или проверкой. Собственная программа проверки этой поставки не заменяет `check_extraction.py` и `check_preparation.py`: последние проверяют другую цепочку происхождения от автоматического извлечения.

## Самопроверка поставки

```powershell
python -m unittest discover -s scripts/convert_chunked_V0_to_V2 -p "test_*.py" -v
```

Фактические результаты изолированных проверок приведены в `verification.json`. Они не означают визуальную или смысловую приёмку материалов и не являются запуском на вашем компьютере.
