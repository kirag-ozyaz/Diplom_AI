# Импорт исправленного Markdown в чанки V2

## Старый и новый способы не смешиваются

**Старый** `scripts/convert_chunked_V0_to_V2/convert.py` оставлен без изменений.
Он читает старые JSONL из `data/chunked` и создаёт `data/chunked_V0`.
Старые `merge.py`, `check.py` и результаты также не заменяются этим архивом.

**Новый** `scripts/import_extracted_to_V2/prepare.py` читает исправленные
`data/extracted/1.1.md` … `1.9.md` вместе с локальными ресурсами.
Он НЕ читает `data/chunked` и НЕ использует старые JSONL вместо исправленного Markdown.
Новый `check.py` проверяет сохранность; новый `merge.py` выбирает главы целиком.
`core.py` и `preservation.py` — внутренние модули, отдельно их запускать не надо.

Архив содержит только новый каталог скриптов, тесты и эту инструкцию.
Версия указана только в имени ZIP, обычные имена скриптов менять не требуется.
Ни исходные документы, ни готовые корпуса, ни ключи доступа в архив не включены.

## Установка

Распаковать архив в корень проекта `X:\Учеба_УИИ\Итоговы_Проект`.
Должен получиться путь `scripts\import_extracted_to_V2\prepare.py`,
а НЕ `V2\scripts\import_extracted_to_V2\prepare.py`.
Установленные ранее файлы старого конвертера заменять не надо.
Нужен Python 3.9 или новее, дополнительные пакеты не требуются.
Все команды ниже выполняются из корня проекта в PowerShell.

## 1. Подготовить исправленные главы

В `data/extracted` должны находиться исправленные Markdown и все файлы,
на которые ведут их локальные ссылки (например `image_1.3/...`).
В `V2/data/chunked` должен оставаться исходный новый корпус V2 из 46 документов,
не результат предыдущего смешанного объединения.

```powershell
python scripts/import_extracted_to_V2/prepare.py
python scripts/import_extracted_to_V2/check.py
```

Новый результат: `data/chunked_manual`.
Отчёт: `data/chunked_manual/_audit/report.json`.
Оригинальные Markdown побайтово сохранены в `_audit/markdown`.
JSONL, ресурсы, происхождение и обратимые замены путей проверяются контрольными суммами.
По умолчанию обрабатываются только главы 1.1–1.9, не все файлы `data/extracted`.

## 2. Посмотреть план (необязательно)

```powershell
python scripts/import_extracted_to_V2/merge.py
python scripts/import_extracted_to_V2/check.py --output V2/results/import_extracted_to_V2/plan
```

Это только архив входов и план, активных чанков в нём **0**.
Без `--apply` скрипт не создаёт рабочий объединённый корпус.

## 3. Собрать отдельный объединённый корпус

```powershell
python scripts/import_extracted_to_V2/merge.py --apply --prefer-manual-chapters 1.1 1.2 1.3 1.4 1.5 1.6 1.7 1.8 1.9
python scripts/import_extracted_to_V2/check.py --output V2/data/chunked_merged_manual
```

Результат: **`V2/data/chunked_merged_manual`**.

Приоритет применяется к **целой главе/документу**, включая вводный текст,
заголовки, все пункты, таблицы и формулы, а не только к совпавшим чанкам.
Главы 1.1–1.9 берутся из исправленного Markdown, остальные документы — из V2.
Заменённые исходные главы V2 и все входные строки с ресурсами сохраняются
в `_audit/inputs`. Обе исходные папки остаются нетронутыми.
Старый `V2/data/chunked_merged` тоже не изменяется.

## Логи и повторный запуск

Весь печатаемый JSON каждой новой команды, включая диагностические ошибки,
дублируется в отдельный UTF-8 файл в `V2/results/import_extracted_to_V2/logs`.
Точный путь указан в `console_log`. Это относится к новым командам;
существующий `V2/scripts/run_pipeline.py` этим архивом не меняется.

Скрипты намеренно **не перезаписывают существующий результат**.
Для повторного импорта после правок используйте новую папку и передайте её
во все следующие команды. Например:

```powershell
python scripts/import_extracted_to_V2/prepare.py --output data/chunked_manual_repeat
python scripts/import_extracted_to_V2/check.py --output data/chunked_manual_repeat
python scripts/import_extracted_to_V2/merge.py --manual data/chunked_manual_repeat --output V2/data/chunked_merged_manual_repeat --apply --prefer-manual-chapters 1.1 1.2 1.3 1.4 1.5 1.6 1.7 1.8 1.9
python scripts/import_extracted_to_V2/check.py --output V2/data/chunked_merged_manual_repeat
```

Если исходные JSONL V2 изменились между импортом и объединением, объединение
останавливается: повторите подготовку в новую папку относительно актуального V2.

## Что сохраняется и что не утверждается

* Текст, математическая разметка, таблицы и порядок текста сохраняются буквально.
  Автоматического исправления нормативного содержания или формул нет.
* Меняются только адреса локальных ресурсов: файлы копируются побайтово в
  `assets/<sha256>.<ext>`, исходная ссылка и её замена записываются в аудит.
* Имя картинки, написанное обычным текстом без ссылки, остаётся обычным текстом.
  Импортёр не угадывает, какую картинку следует вставить; выдаёт предупреждение.
* Весь Markdown покрывается диапазонами, включая преамбулу и заголовки разделов.
  Заголовки разделов сохраняются отдельными контекстными блоками; названия таблиц
  остаются вместе с соответствующим пунктом.
* Длинный пункт делится только на границах пустых строк вне формул и кода;
  единая слишком большая таблица/формула вызывает ошибку, а не обрезается.
* Проверяются наличие и уникальность всех собственных пунктов каждой главы
  относительно V2, однозначность документа/Scope, все файлы и контрольные суммы.
* `source_file` — логическая связь с документом DOCX. Реальное происхождение —
  `manual_markdown_sha256`, `manual_char_start/end`, `manual_span_sha256` и архив MD.
  Это не смещения текста внутри DOCX; поля `source_char_*` оставлены `null`.
* Пользовательские исправления и оставленное без изменений содержание принимаются
  как входной материал проекта. Скрипт не подтверждает их нормативную верность.
* База данных не затрагивается. `ready_for_final_scoring: false` — не ошибка импорта:
  перед оценкой поиска потребуется пересобрать эталонные привязки вопросов к новым
  ID чанков (`qrels`). Автоматической замены активного корпуса/индекса здесь нет.

## Проверка самого комплекта

```powershell
python -m unittest discover -s scripts/import_extracted_to_V2/tests -v
```

Результаты прогона на полученных файлах и ограничения проверки описаны
в `VERIFICATION.md`. `tests.log` — журнал изолированных тестов.
